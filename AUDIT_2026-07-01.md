## Health grade: **B-**

The June remediation work is real, traceable, and tested — this is a genuinely well-engineered single-user RAG/memory service, not a codebase that merely claims to be fixed. Every High and most Medium/Low findings from the prior audit are verifiably closed in code (auth middleware, vault-path containment, atomic index swap with a cross-process lock, batched embeddings, evidence-gated ledger completions), and each fix carries an inline comment citing the finding ID it addresses. The grade is held down to B- by two live gaps that reopen the two most serious prior findings through a *different* door than the one that was closed: (1) the documented deployment recipe — and the actual running container — omits `BRAIN_AUTH_TOKEN` and publishes the port on all interfaces, so the personal vault is reachable read **and** write with zero authentication from the LAN and any neighbor container on the shared Docker network; and (2) the ledger JSON extractor is still not string-literal-aware, so a single stray brace inside a quoted evidence value silently drops an entire night's maintenance — the exact "looks successful, is a no-op" failure class the H3 fix was meant to retire. Neither is a regression of code that was fixed; both are untested paths that survive the fix. Close those two and this is a solid B+/A-.

## What's good

Concrete, verified strengths — these are load-bearing and worth protecting during future edits:

- **Traceable remediation.** Nearly every fix (`auth.py`, `safe_paths.py`, `embedder.py` batching, `indexer.py` locking/signature, `ledger_update.py` JSON handling) carries an inline comment naming the audit finding it addresses. The code is auditable against `AUDIT.md`/`IMPROVEMENTS.md` without archaeology.
- **Resilient core index.** `indexer.py` does an atomic single-file swap (`indexer.py:219-229`) guarded by a cross-process `fcntl` lock, cleans up `*.tmp` on startup, and writes a `_vault_signature` that detects deletes/renames. `searcher.py` refuses to serve a torn index via an `index.ntotal == len(chunks)` consistency guard (`searcher.py:49`). This is backed by `tests/test_indexer_durability.py`, which actually simulates the crash-window scenarios.
- **Solid durability primitive.** `safe_paths.resolve_in_vault` (vault containment: resolve + `.md` check + `vault_root in resolved.parents`) is thoroughly tested (7 cases including symlink-escape) and `atomic_write_bytes` fsyncs before `os.replace` with cleanup on failure. `brain.py` and `tasks.py` both correctly adopt it.
- **Well-tested embedding hardening.** `embedder.py` batching/backoff/timeout is covered by 6 targeted tests (batch splitting, cross-batch ordering, transient-failure retry, retry exhaustion, empty input, explicit client timeout).
- **Defended agentic write path.** `ledger_update.py` gates every check-off behind `filter_completions_by_evidence` (normalized evidence ≥15 chars must be a substring of the note body) and fences untrusted note bodies against prompt injection with `NOTE_FENCE` — both tested in `tests/test_ledger.py`.
- **Deliberate DRY reuse.** `ledger_update.py` imports `moc_linker as ml` and reuses `_post_json`, `scan_notes`, `split_frontmatter`, and `backup_root` rather than reimplementing them.
- **Honest docs.** `README.md` documents its own known gaps in bold warning callouts (e.g. the `LM_BASE_URL` hardcoding at README.md:228-229) rather than glossing over them.
- **Fast, isolated test suite.** 49 tests, temp-vault fixture, deterministic in-process fake embedder, zero network dependency — a good foundation to build the CI/coverage gaps on top of.

## Findings

Severity reflects impact on this single-user homelab threat model. File:line references are against the current tree (`ledger-model-split` @ `466d3b1`).

### HIGH

#### H-1 — Live unauthenticated read+write vault exposure: deploy recipe (and the running container) omit `BRAIN_AUTH_TOKEN` and publish the port unscoped

- **Location:** `deploy/README.md:27` (`ports: - "8053:8000"`), env block `deploy/README.md:31-44` (never lists `BRAIN_AUTH_TOKEN`). Mirrors the live external compose at `/server/docker/compose/mcp/docker-compose.yml`.
- **What's wrong:** The H1 auth fix (`auth.py` `BearerAuthMiddleware`, wired in `mcp_server._build_http_app`) genuinely works, but it is **opt-in** — active only when `BRAIN_AUTH_TOKEN` is set. The repo's own copy-paste deployment recipe lists 10+ env vars (`OBSIDIAN_VAULT_PATH`, `LM_BASE_URL`, `EMBEDDING_MODEL`, `TZ`, `BRAIN_REFRESH_AT_HOUR`, `BRAIN_LINKER_ENABLED`, `BRAIN_LEDGER_ENABLED`, `LINKER_CHAT_URL`, `LINKER_CHAT_MODEL`, `LEDGER_CHAT_MODEL`, `MOC_BACKUP_DIR`) but **never** the auth token, and publishes `"8053:8000"` on all host interfaces rather than `127.0.0.1:8053:8000`. This directly contradicts the project's own guidance (`README.md:396`: "anyone who can reach host:8053 can read and write the vault — so restrict the port to a trusted network") and the loud runtime warning `mcp_server.py` emits when the token is unset.
- **Verification (confirmed live, not hypothetical):** The real external compose matches the recipe verbatim (`"8053:8000"`, no token, no `env_file`); `docker ps` shows the container live on `0.0.0.0:8053->8000/tcp` (v4+v6); `docker inspect` confirms `MCP_HOST=0.0.0.0` and no `BRAIN_AUTH_TOKEN`; the startup log prints `[auth] WARNING: BRAIN_AUTH_TOKEN unset — HTTP tools are UNAUTHENTICATED`; and a live probe of `POST http://127.0.0.1:8053/mcp` **without** an Authorization header returns HTTP 200, not 401. Notably, the same compose scopes a sibling service (`telegram-cowork-mcp`) to `127.0.0.1:8050:8000` with a comment warning that a `0.0.0.0` publish lets any LAN host bypass the gate — the operator knows the loopback pattern but did not apply it here.
- **Impact:** Any LAN device (compromised IoT/guest device, a misconfigured neighbor container on the shared external `backend` network) can `POST http://<host>:8053/mcp` and exfiltrate the entire vault (`brain_query`/`brain_status`), tamper notes (`brain_append_insight`), flip task state (`brain_complete_task`), or trigger expensive rebuilds (`brain_build_index`) with zero authentication. This is exactly the H1 exposure the code fix believed it had closed, reopened by the deployment config. Bounded to LAN + shared Docker network (no evidence of a router port-forward / direct internet exposure), so High rather than Critical for this threat model.
- **Suggested fix:** In both the real compose and `deploy/README.md`, set `BRAIN_AUTH_TOKEN=<generated secret>` **and** bind the port to loopback (`127.0.0.1:8053:8000`), relying on SSH port-forward / SWAG for remote access. Treat "auth code exists" and "auth is turned on in the deployment" as two separate checkboxes.

#### H-2 — `ledger_update.find_json_object` is not string-literal-aware — a stray brace inside a quoted evidence value silently drops the entire night's ledger update (reintroduces the H3 no-op class through a new trigger)

- **Location:** `ledger_update.py:48-89` (`find_json_object`), consumed at `ledger_update.py:284-285` inside `ask_model` (`ledger_update.py:244`).
- **What's wrong:** The scanner increments/decrements a brace-depth counter on every raw `{`/`}` character with no awareness of JSON string literals. A single **unpaired** brace inside any quoted value drives `depth` to zero early, truncating the candidate substring at the wrong offset; `json.loads` raises, the candidate is discarded, and the scan does not recover to the true object boundary. Balanced pairs (`{{daily}}`) still parse — which is why the existing `test_find_json_object_skips_leading_template` misses it. The H3 fix (last-object-with-key selection) is present but added no string-awareness, so this trigger survives it untested.
- **Verification (reproduced live on the current tree):** `find_json_object('{"completed": [{"n": 1, "evidence": "see note re: cost } overrun fixed"}], "new_items": []}')` returns `None`, even though that string is valid JSON. The trigger is plausible because `ask_model`'s prompt instructs the model to copy the proving phrase **verbatim** into `evidence` from untrusted note bodies (`ledger_update.py:266-268`) — a developer's vault full of code/config/Templater `{{...}}` snippets makes an odd brace inside a quoted evidence snippet realistic.
- **Impact:** With `temperature=0`, all retries reproduce the same failure deterministically; `ask_model` falls through to `{"completed": [], "new_items": []}`, and `main()` prints "Nothing to change" and exits 0. Crucially the failure is **masked**: `ask_model` writes "! model call failed" to stderr, but `_run_script` only surfaces stderr when `returncode != 0` — and the exit code is 0 — so the nightly log shows only "Nothing to change", indistinguishable from a quiet night. One stray brace discards the whole night's completions and new items. No data corruption, no crash, no wrong check-off (the item stays open) — but a silently missed nightly detection, indefinitely, if the triggering note persists.
- **Suggested fix:** Make the extractor string-aware (track in-string state, respect `\"` escapes, only count braces outside strings), or drop manual depth-counting entirely and try `json.loads` on progressively larger slices anchored at each `{`, preferring the last one with the expected keys. Add a regression test with an odd/unbalanced brace inside an evidence string.

### MEDIUM

#### M-1 — `brain_status()`'s own `faiss.read_index` call is unguarded — a corrupt index crashes the one tool meant to diagnose that condition

- **Location:** `mcp_server.py:188` (`status["index_vector_count"] = faiss.read_index(INDEX_PATH).ntotal`).
- **What's wrong:** `faiss.read_index()` on a truncated/corrupt file raises `RuntimeError`. This call has only an `os.path.exists` guard and no try/except, whereas `searcher.py:33-38` wraps the identical read in `try/except (json.JSONDecodeError, OSError, RuntimeError)` for exactly this scenario (the L8/M1 fix). The metadata read a few lines earlier in the same function is wrapped; only this raw FAISS read was missed.
- **Impact:** In the crash-window/external-corruption scenario the M1/L8 fixes target (interrupted write, botched restore, bad LiveSync replication of `_brain/`), `brain_query`/`search()` degrade gracefully to `[]`, but `brain_status()` — the first tool an operator/agent reaches for — throws instead of reporting "index corrupt", defeating its diagnostic purpose exactly when it's needed.
- **Suggested fix:** Wrap the read in the same try/except as `searcher.py`, setting `status["index_vector_count"] = "index unreadable (<err>)"` on failure.

#### M-2 — `safe_paths.atomic_write_bytes` silently narrows note permissions (0644 → 0600) on every write

- **Location:** `safe_paths.py:25-42` (`atomic_write_bytes`); called by `brain.append_insight` (`brain.py:104`) and `tasks.complete_task` (`tasks.py:126`).
- **What's wrong:** `tempfile.mkstemp` creates the temp file 0600 (ignoring umask), and `os.replace(tmp, path)` is a rename — the destination inherits the temp file's mode, not the original's. No `os.chmod`/`copymode` restores the original permissions.
- **Verification (reproduced):** a note created 0644, passed through `atomic_write_bytes`, is 0600 afterward.
- **Impact:** Every `brain_append_insight`/`brain_complete_task` permanently and silently downgrades that note to owner-only. In the documented deployment (bind-mounted vault, multi-device LiveSync, external tooling under `moc_linker`/`ledger_update` reading the same files), any other process or host UID/GID that had group/other read access loses it after the first agent write — a cumulative, irreversible-without-manual-chmod side effect undocumented anywhere.
- **Suggested fix:** Before `os.replace`, `os.chmod(tmp, stat.S_IMODE(os.stat(path).st_mode))` when the target exists, else `os.fchmod` to a sane default (0644). Add a regression test asserting mode is preserved across `append_insight`/`complete_task`.

#### M-3 — `searcher.search()` has no embedding-dimension guard — an unmatched model/config change crashes every query (L7 only partially remediated)

- **Location:** `searcher.py:60` (`index.search`), whose only preceding guard is the `ntotal != len(chunks)` check at `searcher.py:49`.
- **What's wrong:** The count guard checks row-count consistency, not embedding dimensionality. `index.search(query_vec, k)` sits outside the try/except that wraps `read_index` + `json.loads`. If a query is embedded at a different dimension than the stored index, FAISS raises a bare, message-less `AssertionError` from the C++ layer (reproduced with the pinned `faiss-cpu` build). `metadata['embedding_model']` is recorded (by `indexer.py:216`) but never compared against the live `config.EMBEDDING_MODEL` before the search.
- **Impact:** If `EMBEDDING_MODEL` is ever changed (hardcoded today at `config.py:14`, but `IMPROVEMENTS.md` H7 proposes making it env-driven) without a `force=True` rebuild, the next `brain_query` raises an unhandled `AssertionError` all the way to the MCP client — the MCP SDK swallows it into an opaque error string with no server-side logging — instead of the graceful "rebuild needed" degradation every other inconsistency scenario gets. `AUDIT.md:239`'s "Overlaps M1" note is inaccurate: the count guard does not cover this. `tests/test_indexer_durability.py` exercises the count-mismatch branch but not the dimension branch.
- **Suggested fix:** After loading metadata, compare `query_vec.shape[1]` (or `index.d`) against the index dimension **and** compare `metadata.get('embedding_model')` to the live `EMBEDDING_MODEL`; return `[]` with a "rebuild needed / model mismatch" log line on either mismatch, matching the existing `ntotal` pattern. Correct the `AUDIT.md:239` note. Add a regression test.

#### M-4 — Nightly LLM-maintenance failures are indistinguishable from a quiet night (endpoint-down masquerades as success)

- **Location:** `ledger_update.py:280-295` (`ask_model`) and `main()`; `moc_linker.py:236-237` (`classify_note` fallback); `mcp_server.py` `_run_script` (stderr printed only on non-zero exit).
- **What's wrong:** `ask_model` returns empty arrays after retry exhaustion (stderr-only diagnostic); `main()` then prints "Nothing to change" and exits 0. `classify_note` defaults every failed note to `{'moc': 'Unsorted', 'desc': ''}` the same way. `_run_script` captures stdout/stderr but only prints stderr `if proc.returncode != 0` — since these scripts exit 0 on model failure, the "! model call failed"/"! classify failed" lines are captured and discarded, never reaching `docker logs`. This is `AUDIT.md` L9/L10 / `IMPROVEMENTS.md` H9, documented as unimplemented and untested.
- **Impact:** If the chat endpoint (llama-swap/LM Studio) is down or misconfigured, nightly ledger/MOC maintenance silently does nothing every night indefinitely, and `docker logs` shows healthy-looking `[linker] exit=0`/`[ledger] exit=0` forever. Compounds H-2 (which produces the same "Nothing to change" signature).
- **Suggested fix:** Track a per-run LLM-failure count and print a loud WARNING (or exit non-zero) when a meaningful fraction of calls failed; in `_run_script`, print the captured stderr tail whenever it is non-empty, regardless of exit code.

#### M-5 — `moc_linker.py` / `ledger_update.py` mutate vault files with non-atomic writes, and none of these write paths have test coverage

- **Location:** `moc_linker.py:301` (`write_mocs`), `moc_linker.py:329` (`tag_notes`), `moc_linker.py:413` (`cross_link`), `ledger_update.py:409` (`main` apply block).
- **What's wrong:** All four call `path.write_text(...)` directly, unlike `brain.py`/`tasks.py` which route through `safe_paths.atomic_write_bytes` (tmp + fsync + `os.replace`). No test anywhere calls `write_mocs`, `tag_notes`, `cross_link`, `backup_file`, or the ledger `--apply` path. (`tests/test_ledger.py` covers the pure logic helpers in-memory but not the on-disk apply.)
- **Impact:** A process kill mid-write (realistic on this host, which gets rebooted for GPU/driver work while the nightly job runs unattended at 3am) can truncate a note or the ledger file. A dated backup exists outside the vault, but there is no corruption detection or auto-restore — recovery is a manual copy-back with no alert.
- **Suggested fix:** Route these four sites through `safe_paths.atomic_write_bytes` (or an equivalent tmp+`os.replace`), and add smoke-level tests calling `write_mocs`/`tag_notes`/`cross_link`/`backup_file` against a temp vault.

#### M-6 — Nightly scheduler/maintenance orchestration has zero test coverage and no structural exception guard

- **Location:** `mcp_server.py` `_refresh_once`/`_run_script`/`_post_refresh_tasks` (~`:281`), `_refresh_loop` (`:312`), `_maybe_start_scheduler` (`:324`).
- **What's wrong:** No test imports or exercises any of these. `_refresh_loop`'s while-body calls `_refresh_once()` then `_post_refresh_tasks()` with no try/except of its own — it survives today only because every callee individually catches `Exception`. `threading.Thread` swallows an uncaught exception in its target by printing one traceback and silently terminating; there is no watchdog/restart and no lasting log signal afterward.
- **Impact:** This is the single most consequential long-running job in the system (it keeps the index and vault maintenance current) and it is completely dark to the test suite. Any future edit that adds an unguarded call inside `_refresh_loop` permanently and silently stops the nightly pipeline with no automated way to catch it.
- **Suggested fix:** Add unit tests for `_seconds_until_hour`, `_refresh_once` (success + exception-swallowed), `_run_script` (non-zero exit, timeout, exception), and `_post_refresh_tasks`' env wiring; wrap the per-iteration body of `_refresh_loop` in its own top-level try/except so a future unguarded failure can't kill the thread.

#### M-7 — Docker/compose healthcheck only proves the HTTP listener is up, not that the brain is functioning

- **Location:** `mcp_server.py:204-207` (`/health`), `Dockerfile:39-40` (HEALTHCHECK), `deploy/README.md:50-55`.
- **What's wrong:** `/health` unconditionally returns `{"status": "ok"}` with no check of index loadability, scheduler-thread liveness, or recent refresh outcome. `brain_status()` is closer to a real health surface but isn't wired into the HEALTHCHECK and doesn't report scheduler-alive or last-refresh-success either.
- **Impact:** Combined with M-4 and M-6, the container can report "healthy" (and never trigger `restart: unless-stopped`) indefinitely while the actual functionality (fresh index, working maintenance) has silently stopped. Matches `IMPROVEMENTS.md` Q3/H9, explicitly marked not implemented.
- **Suggested fix:** Have `/health` (or a separate `/ready`) check `index.ntotal == len(chunks)`, `scheduler_thread.is_alive()`, and time-since-last-successful-refresh against a configurable staleness threshold, returning non-200 on failure.

#### M-8 — Interactive tool-call failures are invisible in container logs

- **Location:** `mcp_server.py:84-160` (`brain_query`, `brain_write_entity`, `brain_append_insight`, `brain_tasks`, `brain_complete_task`, `brain_build_index`).
- **What's wrong:** None of these tool bodies wrap their calls in try/except+log; only `brain_status` has any resilience. The MCP SDK's own `call_tool` handler does not log exceptions before converting them to a client-facing error string. Only the nightly-refresh path was instrumented with `print(...)`; the far more frequent interactive path has none.
- **Impact:** An embedding-endpoint outage, vault permission error, or disk-full hit during an active agent query/write produces zero trace in `docker logs` — the operator's only real-time visibility for this single-container service. The failure is visible only if the calling agent surfaces the raw error text.
- **Suggested fix:** Wrap each `@mcp.tool()` body in a thin try/except that logs (path, args summary, exception) to stderr before re-raising or returning a structured error.

#### M-9 — `moc_linker.classify_note` embeds the raw note body into the prompt with no fence — the injection defense applied to the ledger was never applied to the linker

- **Location:** `moc_linker.py:200` (`f"Note body (truncated):\n{body}\n\n"`), `classify_note` at `moc_linker.py:177`.
- **What's wrong:** `ledger_update.py` wraps untrusted note bodies in `NOTE_FENCE` and neutralizes spoofed delimiters (tested as M13). `classify_note` — in the largest module, run nightly against **every** note — inserts the raw body directly with no fence and no neutralization. The `moc` value is allowlist-snapped (`moc_linker.py:228-230`), but the free-text `desc` is returned unfiltered (`moc_linker.py:231`) and written into note frontmatter, and the classification itself is steerable by a crafted note body.
- **Impact:** Lower blast radius than a ledger check-off (no task-state change), but a note containing injection text can steer its own `moc:` classification (within the allowlist) and inject arbitrary `desc` frontmatter content across the vault. The injection dimension the team clearly ran on the ledger was never run on the linker.
- **Suggested fix:** Apply the same `NOTE_FENCE` + delimiter-neutralization pattern to `classify_note`'s prompt, and sanitize/length-clamp `desc` before writing it to frontmatter. Add an injection test mirroring the ledger's M13 test.

#### M-10 — `mcp_server.py` module docstring overstates `LM_BASE_URL`/`EMBEDDING_MODEL` as env-configurable for the core path

- **Location:** `mcp_server.py:14-21` vs `config.py:13-14` (hardcoded literals) and `README.md:228-240` (accurate).
- **What's wrong:** The docstring's "Environment" block lists `LM_BASE_URL` and `EMBEDDING_MODEL` alongside genuinely env-driven vars, but `config.py` hardcodes both — only the maintenance subprocesses (`_post_refresh_tasks`, now reading `LM_BASE_URL`/`EMBEDDING_MODEL`/`LEDGER_CHAT_URL`/`LEDGER_CHAT_MODEL` at `mcp_server.py:297-298`) read them from env. The same commit that fixed this in `README.md` (with an explicit warning box) never updated the module's own docstring. *(This defect appeared twice in the finding inputs — the two entries are the same issue.)*
- **Impact:** An operator wiring env vars from `mcp_server.py` (the file most likely opened for that) reasonably believes setting `LM_BASE_URL` redirects where `brain_query`/`brain_build_index` send content; in fact core retrieval keeps hitting the baked-in `192.168.0.29:1234`. If the LM Studio host IP changes, this yields silent wrong-endpoint queries that look like a working config change.
- **Suggested fix:** Either thread `LM_BASE_URL`/`EMBEDDING_MODEL`/`CHUNK_SIZE`/`CHUNK_OVERLAP`/`TOP_K` through `config.py` via `os.environ.get()` (`IMPROVEMENTS.md` H7), or add the `README.md` warning to the docstring so the two don't disagree.

#### M-11 — `moc_linker.py`, the largest module and run unattended nightly against every note, has import-only test coverage

- **Location:** `moc_linker.py` (522 lines); `tests/test_smoke.py:11` is its only referent.
- **What's wrong:** No dedicated test for `classify_note`, `extract_json`, `write_mocs`, `upsert_managed_block`, `tag_notes`, `cross_link`, `backup_file`, or `discover_mocs` — unlike every sibling module (`ledger_update.py`: 8 tests, `safe_paths.py`: 7, `indexer.py`: 8, `embedder.py`: 6). `tag_notes` and `cross_link` are the highest-blast-radius write paths in the system (they rewrite every note's frontmatter and append a "## Related Notes" section into every body). Note that `extract_json` here is a *different* parser (non-nested-brace regex) from `ledger_update.find_json_object`, so the H3/H-2 class can regress here independently and silently.
- **Suggested fix:** Add `tests/test_moc_linker.py` mirroring `test_ledger.py` (fake vault + fake chat/embedding endpoint) covering `extract_json`, `upsert_managed_block`/`upsert_related_block` idempotency, and `classify_note`'s fallback-to-Unsorted path at minimum.

### LOW

#### L-1 — `embed_texts` masks the real error with a confusing `TypeError` when `EMBED_MAX_RETRIES=0`
- **Location:** `embedder.py:37-50` (`_embed_one_batch`).
- With `max_retries=0`, `for attempt in range(0)` never runs, `last_exc` stays `None`, and `raise last_exc` raises `TypeError: exceptions must derive from BaseException` instead of the real connection/API error. `EMBED_MAX_RETRIES` is a documented env knob with no stated minimum, and `0` ("disable retries, fail fast") is a plausible operator choice that gets a misleading error at exactly the moment fast, clear failure was requested.
- **Fix:** Treat `max_retries < 1` as 1 minimum, or raise a clear `ValueError` naming the configured value.

#### L-2 — `moc_linker` note backups use a non-timestamped, colliding filename (M8, documented/deferred)
- **Location:** `moc_linker.py:328`, `moc_linker.py:412` — both write `{stem}.bak.md` with no timestamp, unlike the timestamped `backup_file()` helper used for MOC files (`moc_linker.py:281`).
- Two consecutive nightly runs touching the same note overwrite each other's pre-edit backup, so only the most recent survives. Already tracked as M8/deferred; noted for completeness, not a new discovery.
- **Fix:** Apply the existing `backup_file()` timestamp scheme to these two call sites.

#### L-3 — Dead code: `brain.get_or_build_index` is defined but never called
- **Location:** `brain.py:28-31`. A repo-wide grep finds no callers; `__main__` calls `build_index()` directly. Its "official"-sounding name risks a future maintainer building on unused code.
- **Fix:** Delete it, or route `brain_build_index`/`consolidate.py` through it so it isn't orphaned.

#### L-4 — Deprecated `obsidian_brain.py` is baked into the production image
- **Location:** `Dockerfile:27` (`COPY *.py ./`); `.dockerignore` excludes docs but not `obsidian_brain.py`.
- The legacy prototype (its own JSON index, a different default embedding model) ships into every image where nothing imports it — image bloat and a debugging landmine (running it inside the container yields a different model + separate index).
- **Fix:** Add `obsidian_brain.py` (and `obsidian-brain.md`) to `.dockerignore`.

#### L-5 — No CI despite a fast, fully-passing suite
- **Location:** repo root (no `.github/workflows`). 49 tests pass in 0.57s with no network/GPU. `IMPROVEMENTS.md` L5 proposes CI, marked unimplemented.
- Every fix is protected only by developer discipline to run pytest locally.
- **Fix:** Add a minimal GitHub Actions workflow running `pip install -r requirements.txt` + `pytest tests/ -q` on push/PR.

#### L-6 — Malformed numeric env vars crash the whole process at startup
- **Location:** `mcp_server.py:~325` (`int(os.environ.get("BRAIN_REFRESH_AT_HOUR", "3"))` in `_maybe_start_scheduler`, called unguarded before `uvicorn.run()`); `config.py:21-23` (`EMBED_BATCH_SIZE`/`EMBED_TIMEOUT`/`EMBED_MAX_RETRIES` parsed at import).
- A config typo (e.g. `BRAIN_REFRESH_AT_HOUR=3am`) prevents the container from binding a port at all, rather than degrading gracefully.
- **Fix:** Wrap these conversions in a helper that logs a warning and falls back to the default on `ValueError`.

#### L-7 — Audit fixes are pushed but not merged to `master` (process/deploy hygiene)
- **Location:** `master` @ `ffbbcbe` (pre-audit) vs the checked-out, deployed `ledger-model-split` @ `466d3b1` (contains all fixes, pushed to `origin/ledger-model-split`).
- **Framing correction:** an earlier draft finding claimed the remediation was "unmerged **and unpushed**, so production runs vulnerable code." ## What's missing — capability roadmap (ordered by value-to-effort)

These are opportunities, not defects. Ordered best-ratio first.

1. **Full-note & structured read tools** — *value: high · effort: S (a day).* The server exposes only chunk-level retrieval (`brain_query`, 500-char snippets); there is no `brain_get_note`/`brain_recent_notes`/`brain_list_entities`/`brain_backlinks`. The live vault has 60-99KB meeting-transcript notes that chunk-and-dedupe retrieval mangles — "what did we decide June 30" returns three disconnected fragments instead of the note. Add thin `safe_paths`-guarded, index-free read tools reusing existing vault-scan helpers. This is `IMPROVEMENTS.md` H8 and the highest-leverage easy win.

2. **Near-real-time index refresh via `POST /refresh`** — *value: high · effort: M (half day).* The scheduler only rebuilds ~30s after boot and nightly at 3am; there is no inotify/webhook. New meeting notes and the owner's reMarkable→Obsidian hourly OCR output can sit unsearchable for up to 24h. Add a `POST /refresh` route beside `/health` that calls `build_index(force=False)` (reusing its lock/atomic-swap safety) so any vault writer can trigger a refresh after a write. Directly closes the gap between two of the owner's own projects.

3. **Nightly entity extraction** — *value: high · effort: M.* `brain_write_entity`/`_brain/entities/` are built and wired but the live `_brain/entities/` is empty after 4+ weeks — the feature depends on an interactive agent remembering to call it, which never happens. Add a third nightly maintenance script (mirroring `ledger_update.py`: local chat model, dry-run default, managed markers, pre-edit backup) that scans recently-touched notes for new people/projects and calls `write_entity_note`. Finally realizes the "vault-as-substrate" philosophy.

4. **Morning digest of what the nightly pipeline did** — *value: medium · effort: S.* `_post_refresh_tasks` only logs to stdout; the owner's only visibility is `docker logs | grep`. Add a step that composes a 3-line summary (new ledger items, MOCs touched, any exit≠0) and either writes it as a dated vault note (queryable, durable, zero new infra) or pushes it via the existing notification channel. Pairs naturally with M-4 (both need the same failure-count data).

5. **Hybrid keyword+semantic search** — *value: medium · effort: M.* `searcher.search` is pure `IndexFlatL2` with no lexical fallback; the promised cosine re-rank was never wired (`cosine_sim` is dead code in the deprecated prototype). The vault is dense with exact proper nouns/codes ("PJM", "ESS", surnames like "Rekow"/"Fluder") that embeddings miss. A substring/regex prefilter merged with vector results before the dedupe step closes this with no index migration.

6. **Direct human query surface** — *value: medium · effort: M.* The brain is agent-native only. Add a `GET /ask?q=...` custom route that calls `query_brain` and returns HTML/JSON, gated by `BRAIN_AUTH_TOKEN` (or behind Authelia at SWAG). Turns it into a 10-second "ask my vault" page from any device.

7. **Frontmatter-aware indexing with date/topic/person filters** — *value: high · effort: L (multi-day).* `indexer.scan_vault` discards YAML frontmatter entirely; no tags/type/date/topics reach the index (`IMPROVEMENTS.md` L1). The owner's own ledger schema (`type`, `window_start/end`, `topics`, `sources`, `moc`) shows exactly the filtering that would pay off ("decisions about PJM from June"). Requires PyYAML (absent from `requirements.txt`), per-chunk frontmatter in `metadata.json`, filter kwargs on `search()`/`brain_query`, and a full reindex. The single biggest retrieval-quality lever, but it touches the index schema and query API — stage it after the easier read-tool and hybrid-search wins.

8. **Bridge to the owner's other memory system (claude-mem)** — *value: medium · effort: M.* Two parallel personal-memory layers never talk. A nightly bridge reading claude-mem's per-project summaries and writing them as dated insight blocks (via `append_insight`/`write_entity_note`) would make the vault the single source of truth the README claims. Moderate because it requires learning claude-mem's storage/API first.
